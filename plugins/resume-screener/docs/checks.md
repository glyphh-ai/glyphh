# What was checked, and what was not

One limit holds for every number in this file and is not repeated under each: **nothing here is a real person, a
real applicant or a real fraud ring.** Every application used was generated by a program, and every "ring" was made
by code from those applications. A number here shows that a step finds what it was built to find, on cases made
for it. None of it shows that real fraud is caught or that a real person is recognised. **Real-person detection is
not proven.**

Each check's protocol and bar are written and committed before it is run. Results are added after, as they come;
nothing above a result is changed once it is seen.

## The data

A corpus of 2,430 generated job applications (ten roles; each an email with a cover letter and a resume as PDF and
as Word files), split 1,980 train and 450 test, labelled with the fit it was written to have (strong, borderline,
poor) and how much of it a language model wrote (some, mostly, fully). One generator wrote all of it and one
renderer made every file. The train split ships with the plugin as the models' examples (`models/examples`: each
model's cases, not the files); the test split ships nowhere.

The 450 test rows were looked at three times while the screener's models were designed (below). **They are not
used again here.** Every check in this file uses train rows only, with its own held-out part carved from them by a
fixed hash.

## Before this plugin: fit and writing (measured earlier, not re-run)

The `fit` and `made` models and the code that reads an application were designed before this plugin existed, on a
360-row validation split of the train rows, then run once on the 450 test rows (the third and last look):

| | fit | Ada unsure | made (some / mostly / fully) | Ada unsure |
|---|---|---|---|---|
| 450 test rows, read from the PDF files | 94.4% | 41 | 65.3% | 151 |
| 450 test rows, read from the Word files | 93.3% | 31 | 64.9% | 147 |
| chance (three balanced labels) | 33.3% | | 33.3% | |

What it shows: on this corpus, an Ada model seeded with 1,980 labelled applications gives a new one the fit label
its generator was told to write, 94 times in 100, and tells how much was generated 65 times in 100 (it tells
`some` well and cannot tell `mostly` from `fully`). What it does not show: anything about real applicants, about
roles outside the ten, or about text written by a person. The `made` model holds only generated applications; it
cannot say "a person wrote this", and no application known to be written by a real person was tested.

Those numbers were measured on the earlier build. Check 0 below asks whether this plugin's copy of the code still
reads an application the same way.

The file checks (hidden, white or tiny text, edited metadata, tracked changes, characters never seen, marks of
pasting from a chat) cannot be scored on the corpus: one renderer made every file. They are proven only on files
made for the tests (`tests/test_filefacts.py`). The `files` model is never seeded from the corpus.

## Check 0: the plugin reads an application as the earlier build did

### Protocol (written 2026-11-24, before it was run)

- Train rows only. The validation split is the earlier one: in each of the 90 cells (role, fit, generated) the
  rows are ordered by `sha256("glyphh-validation-1:" + id)` and the first 4 are validation (360); the other 1,620
  are the design rows.
- `fit` and `made` are made from this plugin's `models/fit.json` and `models/made.json`. The 1,620 design rows are
  read from their `email.eml` (PDF attachments) by the plugin's code and recorded; Ada's learning is run; the 360
  validation rows are decided once.
- Ada is the real one (its kernel behind Ada Cloud's API and workers, in a throwaway local test database).
- No model other than Ada anywhere.

### Bar

The earlier build scored 95.3% on fit and 65.3% on made on these same validation rows. The plugin passes when it
is within one point of each (fit at least 94.3%, made at least 64.3%).

### What this cannot show

These validation rows were used to design the models, so this is not a held-out score. It only shows the code was
carried over without breaking it.

### Results

Run once on 2026-11-24 on a local Ada. **fit 95.3%** (343 of 360; Ada unsure of 32) and **made 65.3%** (235 of
360; unsure of 107): the same as the earlier build, to the row (the confusion tables are identical). Bar met. The
plugin reads an application as the earlier build did.

## Check 1: this application against the others

### What is checked

The `others` step compares an application with every application held in the `others` model, by Ada's own nearest
precedents, asked one part at a time: work history (employers, titles, each job's dates, education), phrasing (the
summary, the duties, the cover letter) and contact details (phones, email addresses, the name part of each
address, links). It names what comes back at or above a ceiling: the same history under another name, the same
phrasing, a contact detail shared with another name, the same person applying again, a burst of near-identical
applications.

### Protocol (written 2026-11-24, before any ring was made or run)

- Only the 1,980 train rows are used. The 450 test rows are not read.
- The train rows are split by `sha256("glyphh-others-1:" + id)`, in that order: the first 150 are the held-out
  bases, the next 150 the held-out controls, the next 100 the design bases, the next 100 the design controls, and
  the remaining 1,480 the population.
- Each application is read from the manifest's text (email, cover letter, resume). The rings are made by changing
  that text, so no file is rendered.
- From a base application, code makes these, each under a new name, a new email address and a new phone number
  (drawn from fixed lists, never from another row):
  - `renamed`: nothing else changed (the same history under a new name and contacts).
  - `reworded`: a light paraphrase, by a fixed table of word swaps applied to the summary, the duties and the
    cover letter.
  - `reordered`: the resume's sections in another order.
  - `one job changed`: the first job (its title, employer, dates and duties) replaced with a job from another row.
  - `burst`: four renamed copies are recorded first, and a fifth is asked about.
  And from a control application (another person, another history): `shared contact`, the control with the base's
  phone number in place of its own.
- **Design.** Ada holds the population and the design bases. The design rings and the design controls are asked.
  What the step reads, its weights and the similarity at which it speaks (one ceiling per part) are chosen here
  and frozen. The ceilings in `screener/others.py` before the design run (history 0.9, words 0.9, contact 0.3)
  are a first guess.
- **The one held-out run.** Ada holds the population, the design rows and the held-out bases (1,830). The held-out
  rings and the 150 held-out controls are asked, once. A control is an application whose own row is not held; the
  rows it is compared with include others written for the same role and fit by the same generator.
- Caught: the step raises at least one flag other than "the same person applying again". Also reported: how often
  the nearest application it names is the base the ring was made from.
- False alarm: a control with any flag.
- No model but Ada. The ceilings are plain numbers read off the design run.

### Bar (on the held-out run)

| | Caught, at least |
|---|---|
| renamed | 95% |
| reordered | 90% |
| reworded | 80% |
| one job changed | 80% |
| shared contact | 95% |
| burst (flagged as a burst) | 90% |

False alarms: at most 5% of the 150 held-out controls. A miss on any line is reported as a miss.

### What this cannot show

The rings are the easy kind: made by code, from one generator's text, with clean swaps. A ring made by people, or
by a model told to disguise it, is not tested. The corpus's applications were written from shared role specs, so
they may resemble each other more than strangers' applications do, or less than a real posting's do; the false
alarm rate is this corpus's, not a real inbox's.

### Results

Run on 2026-11-24 on a local Ada (the kernel behind Ada Cloud's API and workers, in a throwaway test database).

**Design (100 bases, 100 controls; Ada held 1,580).** Two things were changed on the design rows, then frozen and
committed before the held-out run:

- The phrasing ceiling went from 0.9 to 0.47. At 0.9 only 31 of 100 `one job changed` rings were caught. On the
  design rows a control's nearest phrasing reached 0.43 at most, and the weakest ring's (a reworded one) was 0.50.
- An email address is now read whole when its name part has an apostrophe. Read without it, every O'Brien in the
  corpus had the same address, and controls were flagged for it.

After both: every design ring line at 96 to 100 of 100, and 6 of 100 design controls flagged. The history ceiling
(0.9) and the contact ceiling (0.3) stayed as first guessed.

**The one held-out run (150 bases, 150 controls; Ada held 1,830).**

| | Caught | Bar | |
|---|---|---|---|
| renamed | 150 of 150 (100%) | 95% | met |
| reordered | 150 of 150 (100%) | 90% | met |
| reworded | 150 of 150 (100%) | 80% | met |
| one job changed | 144 of 150 (96%) | 80% | met |
| shared contact | 143 of 150 (95.3%) | 95% | met, by one application |
| burst (flagged as a burst) | 150 of 150 (100%) | 90% | met |
| **controls flagged (false alarms)** | **7 of 150 (4.7%)** | at most 5% | met, by one application |

The nearest application named was the ring's base for 150, 150, 150, 146 (one job changed) and 139 (shared
contact) of 150. The 7 flagged controls: 4 for a shared contact detail, 2 for the same phrasing, 1 for the same
history. On the design rows the flagged controls were looked at: the generator had given two different names the
same email address, or the same work history. Those are the step doing what it says, on a corpus that repeats
itself; a real inbox's rate is not known. Another 7 controls were noted as "the same person applying again" (the
generator reuses names), which is told and never counted as a flag. The 7 `shared contact` rings missed were ones
whose nearest contact was under the stranger's own name, so they read as the same person applying again.

What this shows: on rings made by code from this corpus, the step finds the copy, and it stays quiet on about 95 in
100 unrelated applications of the same corpus. Two lines met their bar by a single application, so the true rates
could sit either side of the bar. What it does not show: that a ring made by people, or disguised on purpose, is
found; or what the false alarm rate is on real applications.

## Check 2: the email's timestamps

### What is checked

`screener/timing.py` reads the `Date` header and every `Received` header and names: no date, no server
timestamps, a date after a server already had the message (or after now), a date more than an hour before the
first server had it, servers out of order, more than an hour between two servers, an hour between 1 and 5 in the
morning on the sender's clock, and three or more other applications arriving within ten minutes.

**The corpus has no real timing.** Its emails were written by one program in one sitting: each has a `Date` and no
`Received` header. So nothing about timing can be scored on it, and the `timing` model is never seeded from it.
Everything below is on headers written for the purpose.

### Protocol (written 2026-11-24, before it was run)

- **2a, the code.** `tests/test_timing.py`: each thing the code names, on a crafted header set that has it and one
  that does not. Bar: every test passes. This shows the code does what it says; nothing more.
- **2b, arriving together, on real Ada.** The `others` model holds, for each application, the ten minutes it
  arrived in. Crafted arrivals are recorded: 40 groups, group g at a base time 3 hours and 97 seconds after group
  g-1 (so the groups fall differently against the clock's tens of minutes); in each
  group one message at the base time and four more at +1, +2, +3 and +4 minutes; and one lone message 90 minutes
  after each base time. Then asked, never recorded: for each group a new message at +2.5 minutes (expected:
  counted with at least 3 others, so a burst), and a new message 45 minutes after each base time (expected: counted
  with none). **Design:** the first 10 groups choose the ceiling for the `when` part (the first guess is 0.4);
  **held-out:** the other 30 groups are asked once. Bar: a burst named for at least 95% of the 30 near messages;
  none named for at least 95% of the 30 far ones.
- **2c, the timing model learns the person's answers, on real Ada.** The model starts empty. 60 crafted emails are
  made by code from a fixed seed: 30 ordinary (2 or 3 servers in order, seconds apart, sent between 08:00 and
  18:00) and 30 with a fault (10 dated after the first server had it, 10 with servers out of order, 10 with more
  than an hour between servers). 40 of them (the first 20 ordinary; the first 7 dated ahead, the first 7 out of
  order and the first 6 slow) are recorded with the answer a person would plausibly give (`fine` for ordinary,
  `suspect` for a fault); Ada's learning is not run. The other 20 (10 ordinary, 10 with a fault) are decided once. Bar: at least 18 of 20 answered as taught. Reported: how many
  Ada was unsure of.

### What this cannot show

Whether any of these timestamp patterns marks an applicant who is not a real person. No real email was used. 2c
shows only that the model repeats a rule it was taught on cases as clean as the ones it was taught; real headers
are messier, and what a real person would answer is not known.

### Results

Run on 2026-11-24 on a local Ada (the kernel behind Ada Cloud's API and workers, in a throwaway test database).

- **2a.** All timing tests pass (`tests/test_timing.py`, 7 tests).
- **2b, design (groups 0 to 9).** Two arrivals that share both of their ten-minute names score 1.0; one name, 0.22
  to 0.28; none, 0.02 to 0.05. The first guess for the ceiling (0.4) counted only the first kind and named a burst
  for 9 of 10 near messages. The ceiling was set to 0.15, between "one name" and "none", and frozen
  (`screener/others.py`).
- **2b, held-out (groups 10 to 39), run once.** A burst was named for **30 of 30** near messages (each counted
  with all 5 of its group) and for **0 of 30** far ones. Bar met (at least 95% and at most 5%).
- **2c, run once.** 40 taught, 20 asked: **20 of 20** answered as taught (10 `fine`, 10 `suspect`); Ada was unsure
  of 4 of the 20, and the person would have been asked about those. Bar met (at least 18). In the crafted set 10 of
  the 60 also fell at an odd hour on the sender's clock, by chance of the seed.

What these show: the arrival windows work as designed on arrivals placed by code, and an empty timing model
repeats a clean rule after 40 answers. What they do not show: anything about real emails or real applicants.

## Check 3: the plugin end to end in Claude

### Protocol (written 2026-11-24, before it was tried)

A real Claude session, run headlessly with this plugin loaded and the Glyphh connector available, is asked to
screen one fixture application. Passed when it runs the steps in order, asks Ada through the connector, and
reports the verdict in the order the skill says. If such a session cannot be run, this says so and nothing is
claimed.

### Results

**Not run.** A headless Claude session could not sign in to the Glyphh connector (it needs a person to sign in),
so no Claude session has run this plugin against Ada. Whether Claude follows the skill's steps as written is
unproven.

What was run instead, on 2026-11-24, on a local Ada with two of the fixture applications, is the plugin's code
around Claude, not Claude:

- **The skill's calls, as connector tool calls.** A script made every call the skill names, in its order, against
  the server's own MCP endpoint: `ada_models`, `ada_model_create` for the six models, `ada_record_many` (300
  examples a model, to be quick), then for each application `ada_facts` four times, `ada_decide` four times,
  `ada_record` to keep it, and `screener_verdict` to show the card. Every call was accepted, the answers were read
  by the plugin's steps as they came, and both verdicts were produced.
- **The setup and a screening through the SDK** (`seed.py`, `run.py`), over HTTP: the six models were made, 1,980
  examples loaded into each of fit, made and others, and learning run; run a second time, nothing doubled (1,980
  held in each). The two fixtures were then screened: strong fit and poor fit, as their generator wrote them; both
  "real person" with nothing found by timing or files (a rule's answer: those models hold nothing); screening with
  `--keep` added exactly one application to `others`.

Both fixtures are train rows, so each met its own example: the fit answers here are a model recognising a case it
holds, not a test of it, and `others` rightly named each as "the same person applying again".

## Not checked at all

- Real applicants, real fraud, real emails' timestamps.
- The Greenhouse signal: written from Greenhouse's Harvest v3 API reference, never run against a real account.
- Voice: not built (docs/voice.md).
- Telling the resume from the cover letter by their words alone (the corpus's file names always say which).
- The file checks on files doctored in the wild.
